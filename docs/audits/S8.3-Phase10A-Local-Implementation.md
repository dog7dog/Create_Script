## 3. W1 の実装（`registry-template/.github/workflows/publish.yml` の `release`）

**API の仕様の確認（GitHub の REST の文書、2026-11-12 に読んだ）**

| API | 文書に書かれていること |
|---|---|
| トークンの失効 | `DELETE /installation/token`。「認証に使っているインストールのトークンを失効させる」。応答は `204 No Content` |
| トークンの作成 | `POST /app/installations/{installation_id}/access_tokens`。JWT が必要。本文は `repositories`・`repository_ids`・`permissions`。App に与えていない権限は、トークンにも与えられない。トークンは 1 時間で失効する。応答の `permissions`・`repository_selection`・`repositories` |
| インストールの取得 | `GET /repos/{owner}/{repo}/installation`（JWT） |

- Phase 7 から使っている失効のエンドポイントは、文書と一致した。
- **実際の GitHub での動作は、未検証**（P-14）。

**実装**
- ジョブの権限は `contents: read` だけ。どのジョブの permissions にも `contents: write` は無い（テストで確認）。
- step の env には `GITHUB_TOKEN`・`GH_TOKEN` が無い。`gh` には、App のトークンだけを `GH_TOKEN` として渡す。
  - App の認証・トークンの取得に失敗したときは、`gh` を一度も呼ばずに止まる（fail-closed）。`GITHUB_TOKEN` への切り替えは無い。
- 順序：
  1. SERIAL・SHA-256 の形を確かめ、ファイルを照合する。
  2. **その後、最初の使用の直前に**、App の JWT を作る。鍵は一時ファイル（0600）に書き、署名の直後に消す。
  3. インストールを取得する。
  4. `{"repositories": [<このリポジトリ>], "permissions": {"contents": "write"}}` でトークンを取る。
  5. **すぐにマスクする。**
  6. 応答で、次のことを確かめる。違えば、何もせずに止まる（その場合も、トークンは失効させる）。
     - `permissions` が `contents: write`（と `metadata: read`）だけであること。
     - `repository_selection` が `selected` で、`repositories` がこのリポジトリだけであること。
- トークンは、シェルの変数だけにある。応答の JSON も、変数からパイプで `jq` に渡し、ファイルに書かない。使い終えたら変数を空にする。
- `trap cleanup EXIT` が 1 つだけで、次の 2 つを行う。
  - 鍵のファイルを消す。
  - トークンを `DELETE /installation/token` で失効させる。失敗したときは、秘密情報を含まない `::warning::` を出す。
  - 正常に終えたとき・失敗したとき・途中で抜けたときのどれでも動く。
- 下書き → アセットの確認 → 公開 → immutable の確認 → `verify` の順序と、同じ serial での停止・失敗の記録は、変えていない。
- 鍵は、environment `publish` の secret `REGISTRY_PUBLISHER_APP_KEY`。App の ID は変数 `REGISTRY_PUBLISHER_APP_ID`（空なら止まる）。
- App の権限（Contents: read and write だけ）・インストール先（このリポジトリだけ）は、GitHub の設定で行う（GOVERNANCE.md・手順書）。

## 5. W3 の検査の内容

**`check-settings --ruleset … --tag-creation-ruleset … --tag-protection-ruleset … [--checks-app-id N --publisher-app-id N]`**
- A・B の両方が必須。片方でも無ければ、使い方の誤り（終了コード 2）。
- 共通：target が `tag`、enforcement が `active`、`conditions.ref_name.include` がちょうど `["refs/tags/index-*"]`、`exclude` が空。
- A：規則がちょうど `[creation]`。回避者がちょうど 1 つで、`Integration`、`always`、`actor_id` は次のとおり。
  - 0（未設定）・15368（GitHub Actions）・Checks App の ID は拒否する。
  - 指定された Publisher App の ID と一致すること。
- B：規則がちょうど update・deletion・non_fast_forward。回避者が空。
- App の ID：正の整数で、2 つが違うこと。main の ruleset の `integration_id` が Checks App の ID と一致すること。

**`check-live-rulesets --repo DIR --live DIR --checks-app-id N --publisher-app-id N`**
- `publish.yml` の `check` ジョブの新しい step が使う。step は、ジョブの読み取りのトークンで `GET /repos/{r}/rulesets` と、`target` が `tag` のものの `GET …/rulesets/{id}` を保存する。
- 処理：
  1. リポジトリの A・B のファイルを、上の規則と App の ID で検査する（ファイルの `actor_id` も、変数の ID と一致すること）。
  2. 同じ名前の実際の ruleset が、ちょうど 1 つずつあることを確かめる。
  3. 実際の ruleset が、同じ規則に通ることを確かめる。規則は「必要なものが含まれる」で判定する。ほかの規則が増えても、制限が強まるだけなので。
- 知っている項目だけを読み、項目が無ければ失敗する。
- **GitHub の文書によると、`bypass_actors` は、その ruleset に書き込める利用者にだけ返される。** 読み取りのトークンでは返されない見込みなので、そのときは「確かめられない」として **失敗し、公開は止まる**。推測で通すことはしない。
- この確認をどう行うか（例：運営責任者が管理者の権限で確認して記録する）は、Phase 10B で、実際の挙動を見てから決める（P-19）。
- **今の雛形のままでは、公開はこの step で止まる見込み**（安全側。GitHub では未検証）。
