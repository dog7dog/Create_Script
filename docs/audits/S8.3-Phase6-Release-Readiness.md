## 3. GitHub Actions の静的解析

### 方法（差分ではなく、ファイルそのものを読んだ）

1. **YAML：**
   - PyYAML の SafeLoader に、重複キーで失敗する構成を加えたもので読んだ。
   - 同じファイルを、Ruby の `YAML.safe_load` でも読んだ。
2. **構造：** 次のことを確かめた。
   - `on` があること（YAML 1.1 で `on` が真偽値として読まれる点を考慮）。
   - job ID の形と重複。
   - `runs-on`。
   - `needs` が存在する job を指すこと。
   - step ID の重複。
   - 1 つの step に `run` と `uses` がちょうど 1 つあること。
   - `permissions` のスコープと値。
   - `environment` の形。
3. **式：**
   - `${{ }}` の括弧の対応。
   - 使える context・関数だけを参照していること。
   - `steps.<id>` が、前にある step を指すこと。
   - `needs.<job>` が、その job の `needs` にあること。
   - `env.<名前>` が定義されていること。
   - job の `outputs` の参照。
4. **シェル：**
   - すべての `run` を、GitHub の既定と同じ `bash` で `bash -n`（構文の検査）にかけた。
   - 定義されていない変数を検出する、独自の検査も行った（jq のプログラムなど、単一引用符の中は除く）。
   - `run` の中に `${{ }}` が無いこと。
5. **検査の道具自体の確認：**
   - 故意に壊した workflow（重複した job のキー、`run` と `uses` の同居、存在しない `needs`、step ID の重複、存在しない `steps.` の参照、`run` の中の式）で、すべて検出されることを確かめた。

## 6. 公開のワークフローの監査（`publish.yml`）

### 処理の順序

期待される順序と、実際の順序の対応：

| 期待される順序 | 実際のジョブ・step | 備考 |
|---|---|---|
| 1. マージ済みの PR の特定 | check: `Find the merged pull request and read its reviews` | |
| 2. 承認の状態の確認 | check: `Check that the merged tree…`（`check-approvals`） | |
| 3. 承認されたツリーと公開するツリーの照合 | 同じ step の前半（`rev-parse PR_HEAD^{tree}` と `HEAD^{tree}`） | 承認の確認より前に行う |
| 4. 署名済みの index の検証 | check: `Check before publishing`（`publish-check`） | **実際には 1 より前に行う** |
| 5. serial の単調な増加 | 同上（直前に公開したものの次であること） | 同上 |
| 6. SHA-256 の記録 | check: `Record the files to publish`（job の outputs） | |
| 7. `publish` environment の承認 | release: `environment: publish` | |
| 8. Release の作成 | release: `sha256sum -c` の後に `gh release create` | |
| 9. 公開した Release の確認 | verify: `check-release` | |

4・5 が 1〜3 より前にあるが、どれも同じ `check` ジョブの中の関門で、`release` は `needs: check` なので、**すべてが成功するまで Release は作られない**。順序の違いに、安全上の影響は無い（P6-I1）。

### 重点の項目

| 項目 | 判定 | 根拠 |
|---|---|---|
| 承認の後に別の内容が公開されない | PASS（模擬） | 承認された head のツリーと、公開するコミットのツリーが同じであること（違えば失敗：模擬の試験）。`release` は、`check` が記録した SHA-256 で 2 つのファイルを照合してから公開する（ファイルを変えると、`gh` の前に失敗：模擬の試験）。チェックアウトは同じ `github.sha` |
| 署名済みの index と Release のアセットの一致 | PASS（静的・テスト）・NOT VERIFIED（実際） | `check-release` が digest を照合する（PublishingTest）。GitHub が digest を返すかは未検証 |
| 同じ serial を再び公開できない | PASS（テスト）・NOT VERIFIED（タグ） | `publish-check` は「already published」で止まる。`gh release create` が失敗すれば、ジョブは失敗する（模擬の試験）。タグの ruleset の効果は未検証 |
| 失敗した公開の安全な再実行 | CONDITIONAL PASS | `release` の前で失敗した場合：何も公開されておらず、再実行してよい。Release の作成の後に `verify` が失敗した場合：Release はすでに公開されていて、再実行すると `check` が「already published」で止まる。手作業での確認と、次の serial での修正が必要（P6-L3、手順書 E-10） |
| `latest` が意図した Release を指す | CONDITIONAL PASS | `gh release create --latest`。公開は `concurrency: publish` で 1 つずつ。書き込みの権限を持つ人は latest を変えられ、公開の確認も latest を基準にする（P4-L6・P6-L4） |
| Release が immutable | NOT VERIFIED | リポジトリの設定。`verify` が `immutable: true` を確かめる（PublishingTest） |
| 公開済みの Release の削除・差し替えの権限 | NOT VERIFIED | immutable な Release では、アセットを差し替えられない、とされる。Release の削除の可否は未確認（P4-L7）。タグの削除・更新は ruleset で禁止 |
| Release の作成の後に検証が失敗した場合 | CONDITIONAL PASS | 自動では戻さない（immutable のため戻せない）。index は署名済みなので、改ざんされたアセットはクライアントが拒否する。手順は手順書に記載 |
| 公開に使うコミットが PR 由来であること | PASS（模擬） | マージ済みの PR が 0 件・2 件、マージされていない PR は失敗。作成者の名前・番号の形も確かめる |
| 承認の再検査 | PASS（模擬） | 承認が不足・古いコミットへの承認・作成者の承認では、失敗する |

### 模擬の実行の方法

- ワークフローのファイルから `run` を取り出し、GitHub の既定の `bash --noprofile --norc -eo pipefail` で実行した。
- `gh`・`curl` は、記録を取って決まった応答を返す偽物に差し替えた。
- git のリポジトリはローカルの bare のもの：base → PR の head（`refs/pull/7/head`）→ squash にあたるコミット。
- ツールは、このコミットから作った `createscript-registry-tool`（3 人のメンテナーの写しを使用）。
- 実際の GitHub の API・イベント・権限・環境は、再現していない。

## 10. 実環境未検証の事項

- GitHub App：作成・権限・インストール・トークンの発行・fork の PR の head SHA へのチェックの作成。

- CODEOWNERS の判定（全メンテナー、運営責任者の PR）。
- environment：`registry-checks` の secret を `pull_request_target` から使えること、`publish` の承認と自分の承認の禁止。
- Actions：外部の協力者のワークフローの承認、`labeled` と再実行のときのイベントの内容、`gh api --paginate --slurp`、`commits/{sha}/pulls`、マージ後の PR の head の fetch。

- GitHub API と GITHUB_TOKEN のレート制限。
- Gradle：wrapper と配布物の公式の checksum、Linux の CI での strict の検証、固定したアクションの SHA が正しい版であること。
- 本物の GitHub の HTTPS での index とパッケージの取得。
- Linux・Windows でのテストと L-5。
