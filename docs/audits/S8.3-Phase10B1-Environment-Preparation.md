## 2. 無料のプランで実施できるか

- **暫定の結論：** public のテスト用のリポジトリで、Actions・environment・GitHub App は無料で使える（文書で確認）。
- **ruleset（main・A・B）が、個人のアカウントの Free で使えるかは未確認。** これが分かれ目。
  - 使えれば、すべて無料で行える見込み。
  - 使えなければ、Team のプランの Organization（有料）か、別の構成の検討が要る。
- そのため、構築の **最初の手順** として、テスト用のリポジトリで ruleset の作成の画面が使えるかを確かめ、使えなければ止める（手順書 H 章）。

## 3. 必要な人員と App

- **人：**
  - 最小 3 人：運営責任者（admin）と、write の権限のメンテナー 2 人。
  - 理由：
    - 2 人の承認と、PR の作成者以外の承認（prevent self-review）。
    - write の権限でタグを作れないことの試験。
  - 必須チェックの偽装の試験（IT-02）まで行うなら、write の権限を持たない外部の協力者が 1 人増えて 4 人。
  - 本番の運営（共同メンテナー 3 人以上）とは別に、テストの段階でも 3 人が要る。
- **App（テスト専用、本番とは別）：**
  - Checks (Test)：Checks: read and write だけ。
  - Publisher (Test)：Contents: read and write だけ。
  - どちらも Webhook は無効、「Only on this account」、テスト用のリポジトリだけにインストールする。Administration は付けない。

## 4. W3 の検証の方法（最重要）

### 4.1 問題

- `check-live-rulesets` は、ジョブの読み取りのトークンで ruleset を読み、`bypass_actors` を検査する。
- 文書によれば、`bypass_actors` は、ruleset に書き込める要求者にだけ返る。
- そのため、今の実装では **正常な公開も止まる** 見込み。安全側ではあるが、運用ができない。

### 4.2 比較

| | 案 A：権限を持つ専用の App で検証 | 案 B：管理者の確認と記録 | 案 C：別の API・方法 |
|---|---|---|---|
| 方法 | 「Ruleset Auditor」App を作り、公開の前にそのトークンで ruleset を読む | 運営責任者が admin の権限で ruleset の JSON を取得し、その内容と `updated_at` を、2 人の承認の PR でリポジトリに記録する。公開の前の確認は、読み取りのトークンで見える項目と `updated_at` を、記録と照合する | `current_user_can_bypass`（誰にでも返る）、rule suites（Administration: read）、ruleset の履歴（Administration: write） |
| 必要な権限 | 文書の「書き込める」の解釈で **Administration: write**。read で足りるかは未確認 | 新しい権限なし（admin は既存。ワークフローは Metadata: read のまま） | `current_user_can_bypass`：Metadata: read。rule suites：Administration: read。履歴：Administration: write |

### 4.3 推奨：案 B'（管理者の記録＋変更の検出＋要求者の回避の確認）

**記録（構築のとき、ruleset を変えたとき）**
1. 運営責任者が admin の権限で `GET /repos/{r}/rulesets/{id}` を取得する。応答に `bypass_actors` が含まれる。
2. その JSON を、`check-settings` と同じ規則で検査する。
3. `github-settings/verified-rulesets.json` に、次のものを記録する。
   - 各 ruleset の `id`・`name`・`updated_at`。
   - 検査に使った項目（target・enforcement・conditions・rules・`bypass_actors`）。
   - 取得した日時と、取得した人のログイン名。
4. 2 人の承認の PR でマージする。PR の審査者は、記録の `bypass_actors` を読める（公開の情報）。

**公開の前の確認（`check` ジョブ、読み取りのトークンのまま）**
1. 記録の内容を、`github-settings/` の A・B と App の ID の規則で検査する。今の `check-settings` と同じ。
2. 実際の ruleset の **見える項目**（target・enforcement・conditions・rules）が、記録と一致する。
3. 実際の ruleset の **`updated_at` が、記録と一致する。** ずれていれば、記録の後に変更があったので **止める**。記録をやり直すまで止まる。
4. `current_user_can_bypass` が、ジョブの `GITHUB_TOKEN` について、A・B ともに `never`。
5. `bypass_actors` が応答に **含まれる** 場合は、今と同じく、それも直接検査する（含まれない場合だけ、記録に頼る）。

**公開の直前（`release` ジョブ、Publisher App のトークン）**
- 同じ ruleset の `current_user_can_bypass` が、A では `always`、B では `never`。
- Publisher App のトークンの権限で読める範囲（Metadata: read）に限る。

**この案が守ること・守れないこと**
- `bypass_actors` の確認を **省略しない**。
  - 記録のときに、admin の権限で全体を確かめる。
  - 公開のたびに、「その後、変わっていないこと」を `updated_at` で確かめる。
- 確かめられない状態では、今と同じく止まる（fail-closed）。
  - 記録が無い、`updated_at` が違う、`current_user_can_bypass` が違う、のいずれか。
- 新しい秘密・権限は増えない（最小権限のまま）。
- **前提：** `updated_at` が、回避者を含むどの項目の変更でも変わること（P-20）。
  - 文書には書かれていないので、PT-5 で確かめる。
  - 確かめられなければ、この案は採れない。そのときは、Administration: read で `bypass_actors` が返るかの結果を見て、再検討する。
- **残る危険：**
  - admin が ruleset を変え、`updated_at` が変わらない形で戻す、などの不正。ただし、admin は信頼の根で、ほかの手段でも保護を外せる。この危険は、今の設計と同じ。
  - 記録と公開の間の短い時間の変更は、次の公開まで検出されない。`release` ジョブの直前の `current_user_can_bypass` の確認で、一部を補う。

**実装（W3'）は、PT-5 の結果を見てから行う。** 今回はコードを変更していない。今の `check-live-rulesets` は、fail-closed のまま残す。
