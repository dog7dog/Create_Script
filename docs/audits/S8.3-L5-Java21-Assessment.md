# S8.3 L-5 — Java 21 での完全修正の可否の評価（2026-11-14）

> 1〜4 章: Java 21 の標準のファイル API だけでは両立しない、という評価（この時点ではコードを変えていない）。
> **5 章: その後、案 A（作業ディレクトリを固定した子プロセス）を実装した（`AnchoredFs`）。判定は 5.5。**

## 1. 競合が残る操作

インストーラーの操作は、すべてプロジェクトの実パスから組み立てたパスで行う。最後の要素は `NOFOLLOW_LINKS`・`CREATE_NEW`・ハードリンク（既存の名前を置き換えない）で守れるが、**途中のディレクトリは、確かめた後にリンクへ差し替えられるとたどられる**。

| 操作 | 場所（コード） | 差し替えたときの結果 | 優先順位への影響 |
|---|---|---|---|
| 決まった名前のファイルの付け替え・置き換え（`createscript.json.new` → `createscript.json`、`createscript.lock.new`、ジャーナル） | `Recovery.replaceFile`・`restoreFile`・`writeJournal`（`SafeIo.replace`・`renameNoReplace`） | 差し替え先に同じ名前の利用者のファイルがあると、それがプロジェクトへ移る（外から消える）。**実測**（下の 3 章の 2・2b） | 1（外の既存ファイルの変更）を守れない |
| 決まった名前のファイルの削除（作業用のファイルの後片付け、取り消しのときのパッケージのファイル） | `Recovery.cleanup`・`PackageDirectories.delete`・`Leftovers`（`SafeIo.deleteFileIfSame` → `deleteVerified`） | 確かめた後の差し替えで、外の同じ名前のファイルを `.delete-…` に付け替え、戻せないことがある | 1 を守れない（消しはしないが、名前が変わりうる） |
| 新しいファイル・ディレクトリの作成 | `SafeIo.writeNew`・`createFile`・`createOwnedDirectory` | 差し替え先に作られる（空のまま止まる。届けば片付ける） | 2（外への新規作成）を守れない |
| パッケージのディレクトリの移動（作業用 → `packages/<name>/<version>`） | `Recovery.forward`（`SafeIo.moveNew`） | 公開されているパッケージのファイルが差し替え先へ移る。移動の後の確認で検出し、成功にしない | 2 を守れない |

**誤った成功は無い:** 移動・書き込みの前後とジャーナルの前後で、実パスと fileKey を確かめ直すため（試験でも 0）。

## 2. Java 21 と macOS で防げない理由

完全に防ぐには、**開いたディレクトリを基準にした操作**（`openat`・`mkdirat`・`renameat`・`unlinkat`・`linkat`、または `O_NOFOLLOW` をすべての要素に効かせる解決）が要る。

| 手段 | macOS・Java 21 の実際 |
|---|---|
| `SecureDirectoryStream`（`openat` 系） | **使えない**。`Files.newDirectoryStream` は `sun.nio.fs.UnixDirectoryStream` を返す（Temurin 21.0.12 で実測）。Linux の JDK は提供するとされる（未検証）が、ディレクトリを作る操作が無い |
| `/dev/fd/N/名前` で開いたディレクトリを基準にする | **使えない**。macOS の `/dev/fd/N` はディレクトリとしてたどれない（「Not a directory」を実測）。Linux の `/proc/self/fd/N` は使えるが、Java 21 から記述子の番号を取る公開 API が無い |
| `NOFOLLOW_LINKS` | 最後の要素だけに効く（POSIX の `O_NOFOLLOW` と同じ） |
| `toRealPath`・fileKey・inode の照合 | 確かめた時点の状態しか分からない（確かめた後の差し替えは防げない） |
| FFM（`openat` などを直接呼ぶ） | Java 22 で正式。Java 21 ではプレビューで、Java 21 を保つ条件に合わない |
| JNI | ネイティブのコードと OS ごとの配布が要る（これまでの方針で禁止） |

決まった名前（`createscript.json`・パッケージのファイルなど）は S8.2 の置き場所と `run` が読む形の一部で、名前を変えると既存の形式・機能を変えることになる。

## 3. 実測（macOS（Darwin 25.3、Apple Silicon）・Temurin 21.0.12、`scratchpad` の試験プログラム）

1. `SecureDirectoryStream`: 使えない（`UnixDirectoryStream`）。
2. 作業用のディレクトリを外へのリンクに差し替えた後の `ATOMIC_MOVE`（`createscript.json.new` → `createscript.json`）: 外の `createscript.json.new`（利用者のファイル）がプロジェクトの `createscript.json` になった。
   - 2b. ハードリンク＋削除（置き換えない付け替え）でも同じ結果。
3. `CREATE_NEW`＋`NOFOLLOW_LINKS` での作成: 外に作られた。
4. 子プロセスの作業ディレクトリ（`ProcessBuilder.directory`）: 起動後に i-node を確かめれば、その後に親のパスが差し替えられても、相対の名前の操作は元のディレクトリに対して行われた。起動の費用は 1 回あたり約 2.6 ms。

競合の試験（`L5RaceTest`、14 方式 × 300 回、前回の対策の後）:
- 誤った成功: 0。
- 利用者のファイル（おとりを含む）の変更・削除: 0。
- 外への書き込み: 77 回（空の `.part-…` がほとんど。中身のあるものは、パッケージのディレクトリの移動の 1 回）。
- 試験で 0 回でも設計上の競合は残る（表 1 の 1 行目は、試験の差し替えの間隔では当たらなかったが、実測 2 で起きることを確かめた）。

## 4. 既存機能を保てる代替案と制約

| 案 | 内容 | 防げるもの | 制約 |
|---|---|---|---|
| A. 作業ディレクトリを固定した子プロセス（POSIX） | ファイルの操作を `/bin/sh` などの子プロセスで行う。起動後に `.` の i-node を確かめ（違えば何もしない）、その中で相対の 1 要素の名前だけを扱う（作成は一意の名前と noclobber、付け替えは `ln`、削除は `rm`。最後の要素のリンクはたどらない） | macOS・Linux で優先順位 1・2 をすべて（設計上） | インストーラーのファイルの操作をすべて作り直す大きな変更。ディレクトリをまたぐ移動は防げないため、作業用のディレクトリを `packages/<name>/` の中へ移す（置き場所の形とジャーナル・後片付けの変更、古いジャーナルの復旧の互換が要る）。`/bin/sh` と OS のコマンドの違い（BSD・GNU）への依存。1 操作あたり数 ms。Windows は今の方式のまま |
| B. Java 22 以降へ移り、FFM で `openat` 系を使う | 開いたディレクトリを基準にした作成・付け替え・削除 | macOS・Linux で優先順位 1・2 をすべて | Java 21 を保つ条件に反する（今回は不可）。Windows は別の実装が要る |
| C. JNI のネイティブの補助 | 同上 | 同上 | ネイティブのコード・OS ごとのビルドと配布・署名。これまでの方針で禁止 |
| D. Linux だけ `SecureDirectoryStream` を使う | Linux で、ファイルの作成・付け替え・削除をディレクトリの記述子を基準にする | Linux でファイルの操作 | macOS は今のまま（条件を満たさない）。ディレクトリの作成は守れない。Linux で未検証 |
| E. 今の対策のまま、既知の制限として扱う | 誤った成功 0、検出、外の空のファイルの片付け | 誤った成功・中身の書き込み（ほぼ） | 表 1 の経路が残る。同じユーザーの権限で動く悪意のあるプログラムが前提（そのプログラムは、インストーラーを使わずに利用者のファイルを直接変えられる） |

推奨: L-5 を完全に閉じるなら A（Java 21 のまま）か B（Java の版を上げる）。どちらも運営の判断が要る。

## 5. 案 A の実装（AnchoredFs）

### 5.1 しくみ

- `createscript-install/.../AnchoredFs.kt`。インストール（`Installer.start` の全体。続行・取り消し・後片付けを含む）の間、プロジェクトの中のファイルを変える
  `SafeIo` の操作は、すべて子プロセス（`/bin/sh` と OS の標準のコマンド。スクリプトは固定の定数）で行う。Windows（`/bin/sh` が無い）は従来のまま。
- 子プロセスは、プロジェクトのルートで起動し、始めに記録したルートの デバイス番号・i-node であることを確かめる。対象のディレクトリまで `cd -P` で 1 段ずつ下り、
  `.` から `..` を段の数だけたどった先がルートであること（今いる場所がルートの子孫であること）を確かめる。作業ディレクトリは i-node で保持されるので、
  その後に途中のディレクトリを差し替えられても、操作は確かめたディレクトリに対して行われる（macOS で実測）。
- 操作はそのディレクトリの中の 1 要素の名前だけで行う。名前・数値は argv で渡し、スクリプトには埋め込まない（名前は `[A-Za-z0-9._@+ -]`、`/`・`.`・`..`・先頭の `-` を拒否）。
- ディレクトリをまたぐ操作は無くした:
  - パッケージの配置: 確かめた写しの中身を `packages/<name>/.placing-<トランザクションの id>` に書き、同じディレクトリの中で `<version>` の名前を付ける
    （作業用の写しは、確かめてから消す。途中で止まった `.placing-…` は、次の続行・取り消しが印と照合して消す）。
  - マニフェスト・ロックファイル・ジャーナル: 確かめた中身を、置く場所と同じディレクトリに書いてから付け替える。

### 5.2 操作ごとの競合の検討

| 操作 | 最後の要素の扱い | 途中の要素 | 残る競合 |
|---|---|---|---|
| ディレクトリの作成 | `mkdir`（既にあれば失敗。リンクも既存とみなす） | 固定済み | 無し（外には作らない） |
| ファイルの作成 | noclobber の `>`（無い名前は O_EXCL）。開いた記述子が、その名前の i-node・リンク数 1・大きさ 0 の通常のファイルであることを確かめてから中身を書く | 固定済み | 無し（ハードリンク・FIFO・リンクへの差し替えは、確かめで止まる） |
| 名前の付け替え（公開） | `link`（既にある名前を置き換えない）→ 元の名前を `unlink` | 固定済み | 無し |
| 置き換え | `mv -f -h`（macOS）/ `mv -f -T`（Linux）。宛先のリンクの先へ入らない。前後で i-node を確かめる | 固定済み | 確かめと mv の間に、同じディレクトリの中で名前を差し替えると失敗する（外は変えない） |
| 権限 | 開いた記述子が公開したファイルの i-node であることを確かめ、`chmod` を記述子（`/dev/fd/3`）に対して行う（macOS・Linux で実測）。変えた後に、名前で（リンクをたどらずに）i-node と権限を読み直して照合する（5.6） | 固定済み | 無し（名前を外のファイルへのハードリンクに替えても、外の権限は変えない: 試験）。変えられない・確かめられないときは失敗にする（0400 のまま成功にしない） |
| 削除 | `unlink`・`rmdir`（リンクそのものを消す。空でないディレクトリは消さない） | 固定済み | 無し（固定したディレクトリの名前だけ） |
| 中身の書き出し（fsync） | パスで読み取りのために開いて force | パス | ほかのファイルを開いても変えない（読み取りのみ） |
| install.lock を開く | 無ければ固定したディレクトリで作り、パスでは CREATE なしで開く | パス | 差し替え先の同じ名前のファイルを開くことはある（中身は変えない）。そのときロックは効かないが、同じユーザーの攻撃者はロックを無視できる |
| 読み取り（確認） | `NOFOLLOW_LINKS` | パス | 読む内容は、印・ジャーナルの SHA-256 と照合する（従来どおり） |

**前提と限界**
- 同じユーザーの攻撃者が、固定した **自分たち（インストール）のディレクトリそのもの** をプロジェクトの外へ移動すると、その後の書き込みは移された先のそのディレクトリに行く。
  利用者の既存のファイル・ディレクトリには書かない（中身は公開されているパッケージと、このインストールの写し）。
- ルートは開始時の実パスの デバイス番号・i-node で決める。開始より前に、利用者のプロジェクトのディレクトリが別のディレクトリと入れ替えられていた場合は、それをプロジェクトとして扱う。
- 子プロセスが答えないとき（例: 名前を FIFO に差し替えて開く操作を止める）は、時間（既定 60 秒）で止め、インストールは失敗する。
- プロジェクトの外の、利用者のキャッシュ（`ArchiveCache`・`RegistryCache`）は対象外（従来の確認のまま）。
- Windows は従来の処理（パスでの操作）のまま。L-5 の競合は Windows では残る（シンボリックリンクの作成には権限か開発者モードが要る。ジャンクションの扱いは未検証）。

### 5.4 Linux の検証で見つけた別の問題

- キャッシュの無い環境で `--dependency-verification strict` にすると、`gradle/verification-metadata.xml` に `junit-bom-5.10.2.pom` のチェックサムが無いため失敗する（`.module` だけが記録されている）。CI でも同じになる見込み。今回は、開発機で strict の検証に通ったキャッシュを写して試験した。検証の設定は変えていない。
- （2026-11-15 追記）`junit-bom-5.10.2.pom` の SHA-256 を、Maven Central（本体と `.sha256`・`.sha1`・`.md5`・`.sha512`）・Gradle Plugin Portal・手元のキャッシュで一致を確かめてから追加した。strict のまま、空のキャッシュで macOS・Linux とも通る（5.7）。PGP 署名は `gpg` が無いため確かめていない。

### 5.5 判定

- **macOS・Linux: L-5 は解決**（プロジェクトの中のファイルを変える操作に、途中のディレクトリの差し替えでプロジェクトの外へ向かう経路は、設計上も試験上も無い）。前提と限界は 5.2 のとおり（固定した自分たちのディレクトリを攻撃者が外へ移した場合・ルートを開始前に入れ替えた場合・キャッシュは対象外）。
- **Windows: 未解決**（従来の処理のまま）。
- 総合: **部分解決**（Windows を含む全 OS では未解決）。
- 5.6 の修正（2026-11-15）の後も、この判定は変わらない（5.7）。

### 5.6 最終不具合修正（2026-11-15）

クリーンビルドで、macOS の `InstallTest` が 1 件だけ偶発的に失敗した（単独の再実行 5 回はすべて成功）。調べた結果と修正は次のとおり。

**原因（再現で確認）**
- 子プロセスが記述子 `3` を確かめる `stat -L /dev/fd/3` が、記述子は開いているのに、まれに「Bad file descriptor」で失敗した。失敗すると、確かめの段階で止まる（安全側の失敗。インストールは UNSAFE で止まり、元に戻した）。
- 多数のプロセスが同時に動くときだけ起きた: 20 並列で 1 万回書くと 2〜3 回。1 プロセスだけでは 1 万回で 0 回、CPU 負荷のある 1 スレッドでは 1,500 回で 0 回。
- Java を使わず、シェルと `stat` だけでも再現した（bash 3.2 で 1 万回中 5 回、dash で 1 万回中 2 回。zsh は 1 万回で 0 回だったが、起きないとは言えない）。macOS の `/dev/fd` の処理（カーネル側）が原因である可能性が高いが、**確定していない**。
- 2 万回の試験で、`/dev/fd/3` が別のプロセスのファイルを指したことは 0 回（起きたのは「読めない」だけ）。
- 失敗の後、macOS の bash が終了時にシグナル処理のループに入り、CPU を使い続けることがあった。インストーラーは失敗のとき子プロセスを強制終了するので、ハングにはならない。このループの原因は分かっていない。
- 同じ調べで、権限を変える段階の欠陥を見つけた: 権限を変える前の確かめや `chmod` が失敗すると、`chmod` を飛ばして 0400 のまま「成功」になりえた（安全性は弱まらないが、権限が意図と違うファイルが残る。実際に起きたことは確認していない）。

**修正（`AnchoredFs.kt` のスクリプト）**
- **読み直し**: 記述子への `stat`（`/dev/fd/3`）が **読めなかったときだけ**、最大 5 回まで読み直す。確かめ済みの記述子への `chmod` も、同じ一時的な失敗を受けるため、最大 5 回まで試し直す（同じ記述子への同じ操作なので、何度行っても結果は同じ）。
- **照合は省かない**: 読めた値（i-node・リンク数・大きさ・種類）が合わないときは、読み直さずにすぐ失敗させる。読み直しても読めなければ失敗させる。
- **権限の確認**: `chmod` の後、名前で（リンクをたどらずに）i-node と権限を読み直し、自分のファイルの i-node であることと、指定どおりの権限であることを照合する。
  - 記述子では確かめられない: macOS の `/dev/fd/N` の `stat` は、ファイルの本当の権限ではなく、記述子の開き方から作った値（書き込み専用なら 200、読み取り専用なら 444）を返す（実測）。
  - 変えられなかった・確かめられなかった: `IOException`（`chmod`）で失敗にする。そのファイルは、名前を付けた直後に止まったものと同じく、書き終えた 0400 のファイルとして扱われる（既存の復旧の処理と `ReadOnlyPartTest` が扱う状態）。
  - その名前が別のものに差し替えられていた: 差し替えたものの権限は変えず、L-5 の失敗（UNSAFE）で止まる。
- **追加した試験（`AnchoredFsTest` は 12 件）**
  - 指定した権限（`rw-------`・`rwxr-xr-x`）になることの確かめ。
  - 権限を変えられないときに失敗すること。macOS で、属していないグループ（`/private/tmp` の下は `wheel`）のファイルに setgid を付けて、実際に `chmod` を `EPERM` で失敗させる。Linux ではこの方法が使えないためスキップする。
  - 公開の直後（権限を変える前）に名前をディレクトリに差し替えると、L-5 として止まり、差し替えたものの権限を変えないこと。

**修正の確認**
