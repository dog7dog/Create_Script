### P4-H1 — 必須チェックは名前だけで指定され、fork のワークフローで偽造できる可能性がある（High）

- **対象**
  - `registry-template/github-settings/main-ruleset.json:27-32`
  - `registry-template/.github/workflows/validate.yml:16-19, 35, 104`
  - `registry-template/GOVERNANCE.md:59`
- **問題**
  - 必須チェックは `{ "context": "validate" }`・`{ "context": "approvals" }` と、名前だけで指定されている。
  - GOVERNANCE.md は、fork のワークフローの実行に承認を求める範囲を「初めての貢献者（first-time contributors）」としている。
  - そのため、2 回目以降の外部の貢献者の PR では、PR に含めたワークフロー（`on: pull_request`）が承認なしに動く。そこで `validate`・`approvals` という名前のジョブを成功させられる。
  - 本物の検査は `pull_request_target` で動く。そのチェックが PR の head のコミットに結びつくか、同じ名前のチェックが複数あるときに GitHub がどれを使うかは、確認していない。
- **成立条件**
  - 攻撃者が、以前にリポジトリへ貢献したことのある外部のユーザーである。
  - GitHub が、偽のチェックで必須チェックを満たしたと判断する（NOT VERIFIED）。
- **影響**
  - 自動の検査が緑に見える。対象は、Release の SHA-256・digest・immutable、ZIP の正規形、数値 ID、利益相反、メンテナーの所属、レジストリが閉じていること。
  - CI を信用した 2 人のメンテナーが承認すると、審査済みの SHA-256 として誤った値が main に入りうる。
  - その後の公開では `publish-check` がリポジトリから index を作り直して照合する。しかし、ZIP の検証をやり直すわけではない。
  - 署名の偽造にはつながらない。
- **再現手順**（GitHub 上で行う必要がある。今回は実施していない）
  1. 試験用のリポジトリに雛形と ruleset を適用する。
  2. 一度貢献したアカウントの fork から、`.github/workflows/x.yml`（`on: pull_request`、ジョブ名 `validate` と `approvals`、`run: true`）を含む PR を出す。
  3. 必須チェックの表示とマージの可否を確かめる。
- **修正方針**
  - Actions の設定で、fork のワークフローの実行に「すべての外部の協力者」の承認を求める。
  - ruleset の「ワークフローの成功を必須にする」（required workflows。リポジトリと参照で固定する）を使い、名前だけの必須チェックをやめる。
  - または、検査の結果を、PR からは作れない名前のコミットステータスとして head SHA に付ける。
  - `.github/` を変える PR を、validate で必ず失敗させる（現在は MAINTENANCE として承認の要件が増えるだけ）。
- **正式公開を妨げるか: はい**（GitHub 上での検証と対処が必要）

### P4-M1 — CODEOWNERS が運営責任者 1 人だけで、運営責任者の PR がマージできない（Medium）

- **対象**
  - `registry-template/.github/CODEOWNERS:6-7`（`*` と `/packages/` のどちらも `@dog7dog` だけ）
  - `main-ruleset.json:21`（`require_code_owner_review: true`）、`bypass_actors: []`
- **問題**
  - GitHub は、PR の作成者が自分の PR を承認することを認めない。そのため、dog7dog が作成した PR は、コードオーナーの承認を満たせない。
  - 対象になる PR: 公開の PR（署名する人が dog7dog の場合）、運営の PR、`TOOL_COMMIT` の更新。
  - さらに、すべての PR が運営責任者 1 人の承認を必要とするので、その人が不在の間はレジストリ全体が止まる。
- **成立条件:** 雛形どおりに設定した。
- **影響:**
  - マージするには、ruleset を一時的に外すか変えるしかない。これは「管理者も回避しない」という方針を、実際の運用で崩すことになる。
  - 運営責任者が単一障害点になる。
- **再現手順:** 設定を読めば確かめられる。GitHub の「作成者は自分の PR を承認できない」という仕様は、GitHub の文書によるもので、今回の実地では確かめていない。
- **修正方針**
  - `/signed/`・運営のファイルに、複数のメンテナー（またはチーム）をコードオーナーとして加える。運営責任者の関与は、`check-approvals` の「運営責任者が作成者か承認者」で担保する。
  - または、署名する人を運営責任者以外にする。
- **正式公開を妨げるか: はい**（公開の流れが詰まる）

### P4-M2 — 通信に失敗すると、保存してある有効な index で続行する（失効を隠せる期間がある）（Medium）

- **対象**
  - `createscript-install/.../RegistryClient.kt:118-130`（`catch (failure: FetchFailure)` から `fromCache`）
  - 同 `:150-170`
- **問題**
  - オンラインで取得に失敗したときは、種類を問わず、保存してある期限内の index を使う。知らせるのは `note:` の 1 行だけ。
  - そのため、通信を妨げる攻撃者は、新しい index（緊急の削除・取り下げ）を有効期限まで隠せる。有効期限は既定で 30 日、最大 90 日。
- **緊急に失効させたパッケージを、古い index でインストールできる条件**（すべて、その版がキャッシュかネットワークから得られる場合）:
  1. `--offline` で、失効の前に保存した期限内の index がある（設計どおり）。
  2. オンラインで、index の取得が失敗した（遮断、DNS、GitHub の障害、404、大きさの上限）。保存してある期限内の index が使われる（P4-M2）。
  3. 初めて使うとき、またはキャッシュを消した後で、攻撃者が古いけれど期限内の署名済み index を届けられる。たとえば、書き込み権限のある者が古い Release を latest にした（P4-L6）、または TLS を破った。
  4. index を使えない状態で、`github:` を直接指定した、またはロックファイルから復元した。「確認できない」と警告して続行する。レジストリが未設定なら、復元は何も表示しない。
  5. `createscript run` は、レジストリを確かめない（設計どおり。インストール済みのものはそのまま動く）。
- **成立条件:** 通信を妨げられること（ローカルのネットワーク、DNS、プロキシ）。
- **影響:** 削除・取り下げの効果が、最大で index の有効期間だけ遅れる。署名と SHA-256 の照合は保たれる。
- **再現手順:** `RegistryClientTest.acceptsSavesAndReusesASignedIndex` の通信が失敗する場合で確認できる（`fallback`、`note` 付きで Available）。
- **修正方針**
  - オンラインの `<名前>@<版>` では、取得が失敗したら、既定で失敗させる（古いものを使うには `--offline` を明示する）。
  - または、保存した index の年齢に上限（例: 7 日）を設ける。
  - `indexValidityDays` を短くする（例: 7 日）。
- **正式公開を妨げるか: いいえ**（ただし、公開前に方針を決めることを推奨）

### P4-M3 — ワークフローでツールを作るときに、Gradle の依存を検証せずに取得する（サプライチェーン）（Medium）

- **対象**
  - `publish.yml:41-43, 72-74`（`contents: write` のジョブの中で `./gradlew` を実行）
  - `validate.yml:76-78, 145-147`
  - リポジトリに `gradle/verification-metadata.xml` が無い
- **問題**
  - Gradle の配布物は SHA-256 で固定されている。しかし、Kotlin のプラグインなどの Maven の依存は、検証のメタデータなしで取得される。
  - 依存が乗っ取られた場合:
    - validate では、「OK」を偽造できる。
    - publish では、同じジョブのランナーの中の書き込みトークンを奪える（ランナーのメモリーからの読み取り）。
- **成立条件:** Maven Central・Gradle Plugin Portal 上の依存の乗っ取り、または取得の経路の改ざん。
- **影響**
  - validate: 検査を迂回できる。
  - publish: Release を作れる（古い署名済み index を latest にするなど）。immutable のため既存のアセットは差し替えられず、署名の偽造もできない。
- **再現手順:** 該当なし（設計の評価）。
- **修正方針**
  - Gradle の依存の検証（`verification-metadata.xml`）を入れる。
  - ツールは権限の無い別のジョブで作り、SHA-256 を確かめた成果物として渡す。
  - publish の書き込みは、`gh release create` の 1 ステップだけを持つジョブに分ける。
- **正式公開を妨げるか: いいえ**（強く推奨）

### P4-M4 — 承認の再検査が手動で、認証なしの API を使い、古い実行を再実行できる（Medium）

- **対象**
  - `validate.yml:102-103`（再実行するか、ラベル `recheck` を付ける）
  - `:149-162`（`curl` で認証なしに reviews を読む）
  - `:166-172`（`HEAD_SHA` はイベントの値）
- **問題**
  1. レビューは `pull_request_target` を起動しない。そのため、承認の後にメンテナーが手で再実行する必要がある。
  2. 「Re-run」は、元のイベントの内容（`head.sha`）を使う。新しいコミットの後に、古い実行を再実行すると、古いコミットに対する承認で成功する。その成功が PR の最新のコミットに結びつくかは、未検証。
  3. GitHub のホストのランナーは IP を共有している。認証なしの API は、1 時間 60 回の制限に頻繁に当たる。
- **成立条件:** (2) はメンテナーの操作の誤り、または悪意。(3) は通常の運用でも起こる。
- **影響**
  - (2) メンテナーの数値 ID・利益相反の検査が、古い状態で通るおそれがある。GitHub 自身の「古い承認の取り消し・最後の push の承認」が適用されていれば、承認そのものは最新のコミットに必要。
  - (3) 失敗する側に倒れるので、安全性ではなく可用性の問題（再実行の手間）。
- **修正方針**
  - ジョブの中で API から PR の現在の head SHA を読み、イベントの値と比べる。違えば失敗させる。
  - `pull-requests: read` の `GITHUB_TOKEN` で API を読む（最小の権限）。
  - レビューで起動する安全な仕組みを検討する（`workflow_run` を使う 2 段の構成など）。
- **正式公開を妨げるか: いいえ**（ただし、P4-H1 と合わせて GitHub 上での検証が必要）

### P4-L1 — L-5: 同じユーザーによるシンボリックリンクの差し替えの競合で、プロジェクトの外へ書き込まれる（Low、未解決）

  - 既存のファイルの上書きは見つからなかった（新しいファイルは CREATE_NEW）。
  - インストールは失敗と判定される（誤った成功は 0）。
- **再現手順:** 9 章の監査用テスト（一時的なもの。手順は 9 章に記録）。
- **修正方針:** 9 章を参照。
- **正式公開を妨げるか: いいえ**（既知の制限として文書化済み。同じユーザーの攻撃者は、もともとプロジェクトのファイルを書き換えられる）

### P4-L2 — 拒否の判断の前に、不要なダウンロードが起こる（Low）

- **対象:** `Installer.kt:293-295`（審査の状態の確認は、依存をすべて解決した後）、`Resolver.kt`
- **問題**
  - `github:` を直接指定した場合は、依存の木をすべて取得してから、削除・SHA-256 の不一致を拒否する。
  - `<名前>@<版>` の場合は、index の閉包に無い依存をアーカイブが書いていると、その依存を初回の信頼（TOFU）でダウンロードしてから拒否する。index の検査を通ったアーカイブでは起きない。
- **影響:** 余分な通信（中身は展開も実行もしない）。
- **修正方針:** 取得するたびに審査の状態を確かめ、すぐに止める。`<名前>@<版>` では、index の閉包に無い取得元を取得の前に拒否する。
- **正式公開を妨げるか: いいえ**

### P4-L3 — キャッシュのルートとその上のディレクトリの権限を確かめない（Low）

- **対象:** `RegistryCache.kt:78-100`（確かめるのは `registry/<owner>/<repo>` の 3 段だけ。ルートは `toRealPath()` でたどる）
- **成立条件:** `CREATESCRIPT_CACHE_DIR` を、ほかのユーザーが書き込める（sticky ビットの無い）共有の場所にした。
- **影響**
  - ほかのユーザーによる差し替えの競合（確認と使用の間）が起こりうる。
  - 差し替えたディレクトリは所有者の確認で拒否されるので、通常は使えなくなるだけ（UNSAFE）。
- **修正方針:** プロジェクトと同じ案 C の確認を、ルートとその上のディレクトリにも適用する。
- **正式公開を妨げるか: いいえ**

### P4-L4 — index の取得の、最悪の待ち時間が長い（Low）

- **対象:** `Http.kt:27-32`、`RegistryClient.kt`（index と署名の 2 つのファイル、署名が合わないときの再取得 1 回）

### P4-L5 — 立ち上げの間（メンテナー 0 人）は、承認の検査が何も求めない（Low）

### P4-L6 — 「latest」の指定に依存している（Low）

- **対象**
  - `RegistryClient.kt`（`releases/latest/download`）
  - `validate.yml:85-86`、`publish.yml:81-82`

- **問題**
  - 書き込み権限のある者は、古い `index-*` の Release を latest に指定できる。

## 9. L-5 の再評価

### 試験の方法（一時的な監査用テスト。実行後に削除し、コミットしていない）

- 場所は、JUnit の一時ディレクトリの中だけ。そこに、プロジェクトと、利用者のファイルを模した「外」のディレクトリ（`precious.txt`・`numbers/notes.txt`）を作った。
- 毎回新しいプロジェクトに、`github:owner/vector-math@v1.2.0`（依存 `numbers`）を、メモリーの中の Release からインストールした。
- 同じ JVM の攻撃者のスレッドが、次のディレクトリをシンボリックリンクに差し替えた（元のディレクトリは退避して、戻す）：
  - packages-name: `.createscript/packages/numbers` → 外の `numbers`
  - packages: `.createscript/packages` → 外
  - transaction: `.createscript/txn-*` → 外の `txn`
  - state: `.createscript` → 外の `txn`
- 差し替えのしかたは 2 通り：
  - 連続: インストールの間ずっと差し替え続ける。
  - once: 乱数で決めた 0〜40 ms の時点で 1 回だけ、約 20,000 回のスピンの間、差し替える。
- 判定:
  - 「外へ書いた」は、外のディレクトリの内容が基準と違った回数。
  - 「既存のファイルの変更」は、基準のファイルの中身が変わった回数。
  - 「誤った成功」は、インストールが成功を返したのに、パッケージが実際のディレクトリに正しく置かれていない、またはロックファイルが通常のファイルでない回数。

### 結果（macOS・Darwin 25.3.0、Apple Silicon、JDK 21.0.12.1）

1 回目（連続の 3 方式、各 420 回、計 1,260 回）:

| 方式 | 試行 | 成功 | 失敗（UNSAFE） | 誤った成功 | 外へ書いた | 既存のファイルの変更 |
|---|---|---|---|---|---|---|
| packages-name | 420 | 0 | 420 | 0 | 0 | 0 |
| packages | 420 | 0 | 420 | 0 | 1 | 0 |
| transaction | 420 | 0 | 420 | 0 | 9 | 0 |

2 回目（8 方式、各 420 回、計 3,360 回）:

| 方式 | 試行 | 成功 | 失敗（UNSAFE） | 誤った成功 | 外へ書いた | 既存のファイルの変更 |
|---|---|---|---|---|---|---|
| packages-name | 420 | 0 | 420 | 0 | 0 | 0 |
| packages | 420 | 0 | 420 | 0 | 0 | 0 |
| transaction | 420 | 0 | 420 | 0 | 24 | 0 |
| state | 420 | 0 | 420 | 0 | 2 | 0 |
| once:packages-name | 420 | 3 | 417 | 0 | 0 | 0 |
| once:packages | 420 | 420 | 0 | 0 | 0 | 0 |
| once:transaction | 420 | 98 | 322 | 0 | 5 | 0 |
| once:state | 420 | 64 | 356 | 0 | 0 | 0 |

- **合計: 4,620 回。プロジェクトの外への書き込みは 41 回、誤った成功は 0 回、既存のファイルの変更は 0 回、予期しない例外は 0 回。**
- 外へ書かれたのは、どれも新しい `.part-<UUID>`（書きかけのファイル。権限 0400）。既存のファイルの上書きは無かった。
- once:packages の成功が 420 回だったのは、差し替えの時点が、`packages` を使う区間とほとんど重ならなかったためと考えられる（この方式で外への書き込みが無いことの、強い根拠にはならない）。

### 既存の安全策の有効性

| 安全策 | 評価 |
|---|---|
| 案 C（ほかのユーザーが書けるディレクトリの拒否） | ほかのユーザーによる差し替えを防ぐ（DirectoryPermissionTest）。同じユーザーには効かない |
| 移動の前後の実際のパス・fileKey の確認（L-5 の改善） | 誤った成功を 0 にした。書き込みそのものは防げない |
| CREATE_NEW・NOFOLLOW_LINKS | 最後の要素のリンクと、既存のファイルの上書きを防ぐ。途中のディレクトリのリンクは防げない |

### JDK 21 で実装できる改善策（どれも完全な解決ではない）

1. 作業用のディレクトリを、0700 の推測できない名前にして、作った直後に fileKey を記録する。これは現在も一部実施している。
2. 書いた後に、書いたファイルの fileKey とパスを照合する。外で見つかったものを、記録と完全に一致するときだけ消す。外に作られたファイルを片付けられるが、作ることは防げない。
3. `.createscript` の下をすべて 1 つのディレクトリの中で扱い、パスの段数を減らす。
4. 根本的な解決には、`openat`・`O_NOFOLLOW|O_DIRECTORY` が必要になる。JDK 21 の標準 API には無いので、FFM を使う必要がある。これは方針で禁止されている。長期の課題。

### Linux と Windows の違い（未検証）

- **Linux:** 同じ POSIX の動作なので、同じように再現する見込み。`renameat2(RENAME_NOREPLACE)` は JDK 21 から直接使えない。**未検証。**
- **Windows:** シンボリックリンクの作成には権限か開発者モードが必要で、ジャンクションでも同様の差し替えができうる。POSIX の権限の確認（案 C）は働かない。**未検証。**

**結論: L-5 は未解決。** 同じユーザーの権限の攻撃者は、新しいファイルをプロジェクトの外に作れる。誤った成功判定と、既存のファイルの破壊は、今回の試験では起きなかった。

## 12. 正式公開を妨げる問題

1. **P4-H1（High）:** 必須チェックの偽造の可能性。GitHub 上で検証し、対処する。
2. **P4-M1（Medium）:** CODEOWNERS が単独の運営責任者で、運営責任者の PR がマージできない。
3. **公開の前提がそろっていない**（発見事項ではなく、公開の条件）:
   - 本番の署名鍵の生成と承認（クライアントに組み込む鍵の一覧は空）。
   - メンテナー 3 人以上（`maintainers.json` は空）。
   - レジストリのリポジトリの作成、`TOOL_COMMIT` の設定、公式リポジトリの名前の確定（P4-I7）。
   - 14 章の GitHub 上の未検証事項の確認（ruleset・CODEOWNERS・environment・immutable な Release・チェックの結びつき）。
   - Linux の CI での実行。

## 13. 推奨する修正の順序

1. P4-H1: required workflows（ruleset）への切り替え、外部の協力者の実行に承認を求める設定、`.github/` の変更の拒否。そのうえで、GitHub の試験用のリポジトリで検証する。
2. P4-M1: CODEOWNERS をメンテナー全員（またはチーム）にし、署名する人の運用を決める。
3. P4-M4: head SHA の照合と、`GITHUB_TOKEN`（`pull-requests: read`）による API の読み取り。
4. P4-M2: オンラインで取得に失敗したときの方針（既定で失敗させる・年齢の上限）と、`indexValidityDays` の短縮。
5. P4-M3: Gradle の依存の検証と、ツールを作るジョブと書き込むジョブの分離。
6. P4-L6・P4-L7: 公開の基準を最大のタグにする。Release の削除への対策。
7. P4-L5・P4-L2・P4-L3・P4-L4・P4-I1・P4-I4: 小さな改善。
8. P4-L1（L-5）: 長期の課題（FFM が必要。現在の方針では禁止）。改善策 1〜3 で影響を減らすかを判断する。
