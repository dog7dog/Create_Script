## 2. 修正の内容

### P6-L1 — GitHub App のトークンの失効

**変更（`validate.yml` の `report`）**
- step の始めに `key=""`・`token=""` と、関数 `cleanup` を定義し、`trap cleanup EXIT` を **1 つだけ** 置いた。
  - 以前の `trap 'rm -f "$key"' EXIT` は削除した。鍵のファイルの削除とトークンの失効を、同じ関数で行う。
  - 鍵のファイルは、JWT の署名の直後にも消し、`key=""` にする。
- トークンを得たら、ほかの何よりも先に `::add-mask::` を出す。トークンはシェルの変数だけにあり、ファイルには書かない。
- `cleanup` は、トークンがあれば `curl -X DELETE https://api.github.com/installation/token` を、そのトークンで呼ぶ。
  - 出力は捨てる。curl のエラーの表示も捨てる。
  - 失敗したときは、秘密情報を含まない `::warning::` だけを出す。
  - step の終了コードは変えない。
- 変えていないもの：権限を checks: write に限ること、このリポジトリに限ること、古い実行では何もしないこと。

**テスト**（模擬：`WorkflowHarnessTest` → `harness.py`）
- 正常に終わったとき：チェックを 2 つ作った後に、DELETE が App のトークンで 1 回呼ばれる。
- チェックの作成が失敗したとき：ジョブは失敗し、それでも DELETE が呼ばれる。
- 失効が失敗したとき：結果は成功のまま。警告だけで、秘密情報は無い。
- App が入っていないとき・古い実行のとき：トークンが無いので、何も呼ばない。
- どの場合も、トークンはマスクの行以外の出力にも、スクリプトが作ったファイルにも現れない。
- `TemplateTest.phase7RulesHold`：trap が 1 つだけ、DELETE がある、マスクが使用より前、トークンをファイルに書かない。

**未検証:** GitHub の `DELETE /installation/token` の実際の応答。ログの実際のマスク。

### P6-L3 — Release の公開の後の検証

**変更（`publish.yml` の `release`。書き込みのトークンを持つ唯一のジョブで、ビルドはしない）**
1. SERIAL と、2 つの SHA-256 の形を確かめる。ファイルを、`check` ジョブが記録した SHA-256 と照合する（従来どおり）。
2. **同じ serial の Release（下書きを含む）が 1 つでもあれば、何も作らずに止まる**（再実行で、同じ serial を無条件に公開しない）。
3. `gh release create … --draft` で、**下書き** として作る。`--latest` は付けない。
4. 下書きを API で読み直し、次のことを確かめる。違えば、**下書きのまま止まる**（公開されず、latest にならない）。
   - その tag の Release が 1 つだけで、下書きであること。
   - アセットがちょうど `index.json`・`index.json.sig` の 2 つで、`state: uploaded` であること。
   - GitHub の digest が、記録した SHA-256 と一致すること。
5. `PATCH releases/<id>`（`draft=false`、`make_latest=true`）で、公開して latest にする。
6. 公開の後の応答で、`draft: false`・tag・`immutable: true` を確かめる。違えば失敗として記録する。
- 失敗するたびに、`::error::` とジョブの要約（`GITHUB_STEP_SUMMARY`）に、状態を記録する。自動の削除・上書きはしない。
- `verify` ジョブ（ツールの `check-release`）は従来どおり。失敗したときは、`if: failure()` の step で要約とエラーを残す。
- 公開の前の、署名・serial・SHA-256 の検証（`check` ジョブ）は従来どおり。
- `GOVERNANCE.md` に「Failed publication」（止まった場所ごとの状態と、人が行うこと）を加え、`SIGNING.md` を改めた。

**残る制約**
- immutable は公開した時点で決まるので、公開の前には確かめられない。公開の後に immutable でなかった場合は、Release はすでに公開されていて latest になっている（失敗として記録する）。アセットは署名済みなので、クライアントは改ざんを拒否する。
- 下書きの digest・`draft` の API の動作・`make_latest` は、GitHub の文書の理解に基づいていて、**実環境では未検証**。

**テスト（模擬）**
- 正常のとき：下書きとして作られ（`--draft` あり、`--latest` なし）、下書きの確認の後に PATCH（`draft=false`、`make_latest=true`）が呼ばれ、公開済みで immutable になる。
- digest の不一致・余分なアセット・足りないアセット：下書きのまま止まる。PATCH は呼ばれず、要約に記録される。
- 公開したのに immutable でない：失敗し、記録され、削除はしない。
- 既存の Release（公開済み・下書き）がある状態での再実行：何も作らずに止まる。
- `gh release create` の失敗：公開されない。
- 照合の後にファイルが変わった・SERIAL や SHA-256 の形が不正：Release の操作の前に止まる。
- `verify` の失敗の記録：`if: failure()` だけで動き、要約とエラーを残す。

### P6-L4 — `index-*` のタグの保護

`GOVERNANCE.md` の「Index tags and releases」に、整理した方針を書いた。

| 要件 | 実現の方法と制約 |
|---|---|
| 作成の後の更新・削除の禁止 | `index-tags-ruleset.json`（`update`・`deletion`・`non_fast_forward`、回避者なし）。実環境未検証 |
| 管理者の回避の原則禁止 | 回避者なし（`bypass_actors: []`）。ただし、管理者は ruleset 自体を変えられる（既知） |
| 通常の利用者がタグを作れない／公開する主体だけが作れる | **GitHub の設定だけでは、今の構成では実現しない。** 作成を禁止すると、回避者のいない ruleset では、公開のワークフロー（`GITHUB_TOKEN`）もタグを作れなくなる。公開専用の GitHub App（または deploy key）を、タグの作成に限って回避者にする構成が必要。これは、`contents: write` を持つ 2 つめの App になるので、この雛形には入れていない（運営の変更として別に判断する） |
| 別の名前の Release・latest の変更 | **設定では防げない。** 書き込みの権限を持つ人は、ほかの名前の Release を作り、latest を変えられる。保存した状態のあるクライアントは古い index を巻き戻しとして拒否するが、状態の無いクライアントは期限内の古い index を受け入れうる。書き込みの権限をメンテナーに限ること、index の有効期間、latest の監視（公開のたびに、latest が最大の `index-<serial>` であることを確かめる）で、影響を限る |

- 将来のクライアント側の対策（今回は実装しない。コードの変更として承認が必要）：
  - `releases/latest` のリダイレクトの先の tag が、受け取った index の serial と一致すること（`index-<serial>`）を確かめる。
- ruleset の JSON は変更していない。

### P6-L5 — `git archive` によるファイルの欠落

**変更（`publish.yml` の `check`、承認の再検査の step）**
- `BEFORE`（push イベントの、push の前のコミット）を、16 進数 40 桁であることで確かめる。
- `git merge-base --is-ancestor "$BEFORE" HEAD` で、公開するコミットの祖先であることを確かめる。PR は、この値を決められない。
- `git ls-tree -r -z --full-tree "$BEFORE"` の一覧から、各ファイルを `git cat-file blob` で **生のまま** 取り出す。
  - `.gitattributes` の処理（export-ignore・eol・filter）は使わない。`.git` は含まれない。
  - モードが `100644`・`100755` でない項目（シンボリックリンク 120000、サブモジュール 160000 など）は拒否する。
  - `..`・`.`・空の要素・`.git` を含むパスは拒否する。
  - ファイルが 0 個なら拒否する。
- 出力の前に `::stop-commands::` を出す（パスの名前がワークフローのコマンドとして読まれない）。

**テスト（模擬）**
- **欠落の再現：** base に `.gitattributes`（`maintainers.json export-ignore`、`.github/CODEOWNERS export-ignore`）があるとき、従来の `git archive` では、両方のファイルが消える。
- **修正：** 同じ条件で、base は完全で、承認の検査が通る。
  - 取り出したファイルの集合が、`ls-tree` の追跡ファイルと完全に一致する。
  - 中身は生の blob と同じ。
  - `.git` は無い。
- base にシンボリックリンクがあれば拒否する（`mode 120000`）。
- base が祖先でなければ拒否する。

**eol の属性について（新しく分かったこと）**
- `.gitattributes` に `* text eol=crlf` があると、base は生の blob（LF）だが、公開するコミットの通常のチェックアウト（`actions/checkout`）は CRLF になる。
- そのため、すべてのファイルが変わったように見え、運営の変更として運営責任者の承認が必要になる。
- `publish-check` も、正規形でないファイルや署名の不一致として拒否する。
- つまり、**緩む方向には働かず、失敗する側に倒れる**（模擬の試験で確認）。
- レジストリのリポジトリに `.gitattributes` を置かないことを推奨する。ツールで拒否する変更は、今回は行っていない。
