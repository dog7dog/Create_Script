## 3. L-5 の原因の分析

| 項目 | 分析 |
|---|---|
| 攻撃者に必要な権限 | 利用者と **同じユーザーの権限** で動くプログラム。ほかのユーザーによる差し替えは、案 C（S8.2：プロジェクトとその上、`.createscript` の下に、ほかのユーザーが書き込めないこと）で防いでいる |
| 攻撃者が変更できるディレクトリ | 同じユーザーなら、プロジェクトのディレクトリ、`.createscript`、`txn-*`、`packages/<name>` のどれでも、名前を変えたり、リンクに置き換えたりできる |
| インストーラーが信用しているパス | 始めに `toRealPath` で決めたプロジェクトの実際のパス（`layout.root`）と、その下の決まった名前。すべての操作は名前（パス）で行う |
| 差し替えが成功する時点 | 確かめた（`SafeIo.chain`・fileKey）後で、ファイルの作成（`FileChannel.open`）・名前の変更（`Files.move`）が、途中のディレクトリを名前でたどるまでの間 |
| `NOFOLLOW_LINKS` で防げる範囲 | **最後の要素** がリンクであること（そこにリンクがあれば、たどらずに失敗する）。**途中のディレクトリ** のリンクはたどる（POSIX の `O_NOFOLLOW` と同じ） |
| TOCTOU | 確認と操作の間に、パスの意味が変わる。Java 21 の標準 API には、開いたディレクトリを基準にする `openat`・`renameat` が macOS では無い（`SecureDirectoryStream` は無く、`UnixDirectoryStream` が返る：Phase 5 の実測） |
| 既存のファイルの上書き | **新しいファイルは CREATE_NEW なので、上書きしない。** 置き換えない移動（`Files.move` を REPLACE_EXISTING なしで）は、JDK が先に存在を確かめてから rename するので、その間に作られた同じ名前のファイルを置き換えうる。ただし、置き場所の名前は乱数（UUID）を含むか、マニフェスト・ロックファイルである。マニフェスト・ロックファイルの置き換え（`ATOMIC_MOVE`）は、直前に、読んだときと同じ（SHA-256・fileKey）ことを確かめる。**理論上は、その確認と rename の間にプロジェクトのディレクトリを差し替えると、別の場所の同じ名前のファイルを置き換えうる**。試験（root 方式 840＋420 回）では一度も起きていないが、不可能とは言えない |
| 作られるもの | 試験で観測したのは、`txn` の差し替えによる新しい `.part-<UUID>`（0400）と、`packages/<name>` の差し替えによる、置いたパッケージのディレクトリ（中身は公開されているパッケージのファイル）だけ |
| 成功の判定への影響 | 移動の前後に実際のパスと fileKey を確かめ、ジャーナルを書く前後にも確かめるので、誤った成功は観測されていない（全試験で 0）。最後の確認の後の差し替えは `install` では気づけず、`run` が `.createscript/packages` のリンクを拒否する |
| macOS | 上のとおり。`SecureDirectoryStream` は無い |
| Linux | JDK の実装は `SecureDirectoryStream`（openat 系）を提供するとされる。**未検証**。ただし、この API にもディレクトリを作る操作は無い |
| Windows | シンボリックリンクの作成には、権限か開発者モードが必要。ジャンクション（reparse point）が NIO でどう見えるか（`isSymbolicLink`・`isOther`）は、**未検証**。POSIX の権限の確認（案 C）は働かない |

**同じユーザーの権限の攻撃者への防御には、限界がある。** そのプログラムは、インストーラーを使わなくても、利用者のすべてのファイルを直接書き換えられる。L-5 で増える能力は「インストーラーに、利用者が選んだのではない場所へ、新しいファイルを書かせる」ことに限られ、内容は公開されているパッケージとジャーナルである。

## 4. L-5 の対策案の比較

| 候補 | 効果 | 危険・費用 | 判断 |
|---|---|---|---|
| A1 `SecureDirectoryStream` | 開いたディレクトリを基準に、作成・移動・削除ができる（途中の差し替えの影響を受けない） | macOS の JDK 21 では使えない（実測）。Linux でも、ディレクトリの作成ができない。Linux だけ別の経路を持つと、二重の実装と検証が要る | 実装しない |
| A2 `NOFOLLOW_LINKS`・`CREATE_NEW`・`FileChannel.open` | 最後の要素のリンクと、上書きを防ぐ（実装済み） | 途中のディレクトリには効かない | 既存の対策のまま |
| A3 `ATOMIC_MOVE` | 名前の付け替えを原子的にする（実装済み） | パスでたどるので、途中の差し替えには効かない | 既存の対策のまま |
| A4 `toRealPath`・fileKey・inode の照合 | 差し替えを **事後に** 見つけて、成功にしない（実装済み。誤った成功 0） | 書き込みそのものは防げない | 既存の対策のまま |
| B1 ファイルごとに、書いた直後に位置を確かめて止める | 一度外へ出た後の、続く書き込みを減らす | 試験では、外への書き込みは 1 回に 1 ファイル程度（23 回で 22 ファイル）。続く書き込みはほとんど無く、**効果を測れない**。処理と分岐が増える | 実装しない |
| B2 外へ出たファイルを見つけて消す | 残るファイルを減らしうる | **プロジェクトの外で削除をする**ことになる。再度の差し替えで、別の場所の同じ名前のものを消す危険がある | 実装しない（危険） |
| B3 作業用のディレクトリを、プロジェクトの外（キャッシュなど）に置く | — | 同じユーザーの攻撃者は、そこも差し替えられる。ファイルシステムをまたぐと、原子的な移動ができず、写すことになる（S8.2 N-3 で避けた形） | 実装しない |
| B4 段数を減らす（`.createscript` の下を浅くする） | 差し替えられる場所を少し減らす | 置き場所の形（S8.2 の `.createscript/packages/<name>/<version>`、`run` の読み取り）を変える。互換性に影響 | 実装しない（範囲の外） |
| B5 開始の前とコミットの直前の確認、fail-closed | 実装済み（案 C、移動の前後、ジャーナルの前後） | — | 既存の対策のまま |
| C1 Linux の `openat`・`renameat2`・`O_NOFOLLOW\|O_DIRECTORY` | 根本的な解決になる | Java 21 の標準 API には無い。FFM（Java 22 で正式）か JNI が必要で、今回は禁止 | 将来の設計として記録 |
| C2 macOS の `openat`（macOS 10.10 以降）・`renameatx_np` | 同上 | 同上 | 将来の設計として記録 |
| C3 Windows の reparse point の扱い（`FILE_FLAG_OPEN_REPARSE_POINT`） | ジャンクションの差し替えへの対策 | 同上。未検証 | 将来の設計として記録 |

**FFM・JNI の評価（導入しない場合の記録）**

| 観点 | FFM | JNI |
|---|---|---|
| 導入のコスト | Java 22 以降で正式。Java 21 ではプレビューで、`--enable-preview` が要る（Java 21 を保つ方針に合わない） | C のコードと、OS・アーキテクチャごとのビルドが要る |
| 保守 | 呼び出しの定義を OS ごとに持つ | ネイティブのコードの保守 |
| 配布 | 追加のファイルは要らない | ネイティブのライブラリを、OS ごとに同梱する |
| 署名 | 影響しない | macOS の公証・署名の対象が増える |
| クロスプラットフォーム | POSIX の 2 種と Windows で、別の実装 | 同左 |

将来、Java 22 以降へ移るときに、FFM で `openat` 系を使う設計を検討する（S8.3 の範囲の外）。

**結論：** Java 21 の標準 API だけで、L-5 を閉じる低リスクな方法は無い。**製品のコードは変更せず、L-5 は未解決のままとする。** 単なるパスの確認の追加で解決したとは判断しない。

## 7. 残存リスク

- **L-5：未解決。**
  - 同じユーザーの権限のプログラムは、インストール中に、プロジェクトの外へ新しいファイルやパッケージのディレクトリを作らせうる（観測では、インストールの 0.2〜0.7%）。
  - 理論上は、マニフェスト・ロックファイルの置き換えの直前の、狭い時間の窓で、プロジェクトのディレクトリを差し替えれば、別の場所の同じ名前のファイルを置き換えうる（観測されていない）。
- **利用の制限（docs/packages.md）：** 信頼できないプログラムを同じユーザーで動かしている環境では、インストールを行わない。プロジェクトは、自分だけが書き込めるディレクトリに置く。
- **GitHub の実環境の試験とは別の問題：** GitHub の設定がすべて正しくても、L-5 は解決しない。

## 8. P6-L4 の原因と制約

- **原因：** 公開のワークフローは、`release` ジョブの `GITHUB_TOKEN` で Release とタグを作る。タグの ruleset で作成を禁止すると、回避者がいない限り、このワークフローも作れない。
  - `GITHUB_TOKEN` は、書き込みの権限を持つメンテナーと区別できる「公開の主体」にはならない。
  - GitHub Actions の App を回避者にできるかは不明。できたとしても、ほかのワークフローも同じ App なので区別にならない。

GitHub の仕様について、**確認済みの事実と、文書や理解に基づく推測を区別する**。今回は、どれも実環境で確認していない。

| 項目 | 状態 | 内容 |
|---|---|---|
| ruleset でタグの作成・更新・削除を制限できる | 推測（文書の理解） | repository ruleset は、target `tag` で、`creation`・`update`・`deletion`・`non_fast_forward` を持てる |
| GitHub App を回避者にできる | 推測 | `bypass_actors` の `actor_type: Integration`（インストール済みの App）。`bypass_mode: always` |
| 回避は、その ruleset のすべての規則に及ぶ | 推測 | そのため、作成だけを許す ruleset を分ける設計にした |
| `GITHUB_TOKEN` との違い | 推測 | `GITHUB_TOKEN` は GitHub Actions の App として動き、特定のワークフローや主体だけを回避者にはできない |
| App のインストールのトークンで Release を作る権限 | 推測 | Contents: read and write |
| immutable な Release | 推測 | 公開の後は、アセットとタグを変えられない。Release の削除の可否は不明（P4-L7） |
| `latest` を変える権限 | 推測 | Contents の書き込みの権限があれば、`make_latest` を変えられる |
| 管理者の回避 | 推測 | 回避者に含めなければ、規則は管理者にも及ぶ。ただし、管理者は ruleset 自体を変えられる |
| write の権限と Release の操作 | 推測 | write の権限があれば、Release の作成・編集・削除と、タグの作成ができる（ruleset が無ければ） |
| Organization の ruleset と、必要なプラン | 不明 | Organization の規則の一部は、有料のプランでだけ使えるとされる。確認が必要 |

## 9. タグの保護の 3 案の比較

| 基準 | 案 1：`GITHUB_TOKEN` のまま | 案 2：公開専用の GitHub App | 案 3：Organization と専用の公開の権限 |
|---|---|---|---|
| セキュリティ | タグの作成の主体を限定できない（write の権限があれば作れる）。更新・削除は禁止できる | 作成を App だけに限定できる。App の鍵は `publish` environment の承認の後だけ使える。更新・削除は、回避者のいない別の ruleset で禁止する | owner の分散と、チームによる権限の分担ができる。ただし、作成の主体の限定には、結局、回避者（App・チーム）が要る |
| 実装の難しさ | 変更なし | `publish.yml` の `release` ジョブで App のトークンを作る（`report` と同じ形）。ruleset を 2 つに分ける | リポジトリの移動、チーム、Organization の ruleset。案 2 と組み合わせることになる |
| 運用の負担 | 小さい | App を 1 つ追加（鍵のローテーション、インストールの管理） | Organization の管理、プランの確認 |
| 鍵の管理の負担 | 追加なし | App の秘密鍵が 1 つ増える（environment の secret） | 案 2 と同じか、それ以上 |
| GitHub の仕様の変更への耐性 | 高い（単純） | 中（App のトークン・回避者の仕様に依存） | 中〜低（プランや Organization の機能に依存） |
| 3 人以上の共同運営との整合 | 承認の流れは同じ | 公開は、2 人の承認と environment の承認の後だけ。App を操作できる人を限定できる | owner を複数にでき、共同運営に最も合う |
| 残る制約 | 作成の主体、別の名前の Release、latest | 別の名前の Release、latest、管理者による ruleset の変更、App の鍵を持つ人 | 案 2 と同じ。加えて、Organization の owner |

## 10. 推奨するタグの保護の方式

**案 2（公開専用の GitHub App を、`index-*` のタグの作成の唯一の回避者にする）を推奨する。採用は承認待ちで、確定していない。**

理由：
- `index-*` のタグを作れる主体を、メンテナーの write の権限と区別して限定できる、唯一の案である。案 1 では限定できず、案 3 でも結局、回避者が要る。
- 鍵を `publish` environment の secret にすれば、2 人の承認と environment の承認を経た `release` ジョブだけが使える。
- `report` ジョブと同じ形（トークンの限定・マスク・失効）で実装でき、既存の設計と一貫する。
- 書き込みの権限が、ジョブの `GITHUB_TOKEN` から App に移るので、`release` ジョブの `GITHUB_TOKEN` を読み取りだけにできる。
- 案 3（Organization）は、owner の分散のために、案 2 とは別に検討する価値がある（手順書 A-3）。ただし、タグの作成の主体の限定には不要。

設計の詳細は GOVERNANCE.md の「Proposed: a publishing GitHub App」：
- App の権限（Contents: read and write だけ、このリポジトリだけ）。
- 鍵の保管（environment `publish` だけ）。
- 承認の流れ（PR の 2 人の承認 → マージ → `check` → environment の承認 → `release`）。
- 2 つのタグの ruleset（作成：App だけが回避者／更新・削除：回避者なし）。
- 緊急の停止（ワークフローの無効化、environment の制限、App のインストールの停止と鍵の削除）。

**案 2 でも残る制約**
- 別の名前の Release の作成と、`latest` の変更は防げない。クライアント側で、`latest` の tag が `index-<serial>` であることを確かめる変更を、別に検討する。
- 管理者は ruleset を変えられる。
- App の鍵を持つ人は、`index-*` のタグと Release を作れる（ただし、index に署名はできない）。
