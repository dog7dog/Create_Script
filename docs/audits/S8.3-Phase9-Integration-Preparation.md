## 2. 設計上の決定

| # | 決定 |
|---|---|
| D-1 | **公開専用の GitHub App（Registry Publisher App）を使う方式を採用する。** 必須チェックを発行する Registry Checks App とは、別の App にする |
| D-2 | Checks App：Checks: read and write だけ。check run の作成だけに使う。Release・タグ・コンテンツは扱わない（実装済み） |
| D-3 | Publisher App：Contents: read and write だけ。承認された index の Release の公開と、`index-*` のタグの作成にだけ使う。必須チェックの発行や PR の承認はしない。署名鍵には触れない |
| D-4 | どちらの App も、インストール先はレジストリのリポジトリだけ。トークンは、そのリポジトリと必要な権限に限って発行し、マスクし、step の終わりに失効させる |
| D-5 | 鍵の置き場所：Checks App は environment `registry-checks`、Publisher App は environment `publish`（承認の後だけ）。本番の index の署名鍵は、オフラインだけ（GitHub の secret に置かない。Actions の中で署名しない） |
| D-6 | タグの ruleset を 2 つにする。A：`index-*` の作成を禁止し、回避者は Publisher App だけ。B：更新・削除・non-fast-forward を禁止し、回避者なし。**A の回避者がタグの作成にどう作用するかは、未検証**（前提 P-4・P-5） |
| D-7 | `release` ジョブの `GITHUB_TOKEN` は、移行の後は読み取りだけにする |
| D-8 | 公開の流れは、16 段階（architecture の 4 章）。今の実装と、公開の PR を挟む 2 段の PR の流れを保つ |
| D-9 | テストと本番は、別のリポジトリ・別の App・別の鍵・別の environment で分ける。**本番の CLI・ツールに、信頼する鍵・リポジトリ・URL を変える経路を加えない。** テストには、テスト専用のビルドを使う |
| D-10 | GitHub の仕様の前提が誤っていた場合の代替案を、あらかじめ決めておく（architecture の 3 章） |

## 3. 未検証の事項

GitHub の実環境では、何も確かめていない。前提の一覧は、architecture の 7 章（P-1〜P-17）。主なもの：

- **P-1：** `integration_id` を指定した必須チェックで、偽装したチェックが満たされないこと（IT-02）。
- **P-4・P-5：** ruleset A が、admin・write の利用者によるタグの作成を拒否し、Publisher App の回避で、Release の公開のときのタグの作成が許されること（IT-21・IT-09）。
- **P-6・P-7：** ruleset B が、Publisher App・admin を含めて、更新・削除を拒否すること（IT-22）。
- **P-8〜P-10：** 下書き・digest・immutable の動作（IT-11〜IT-13）。
- **P-13：** environment の secret が、承認の後だけ渡ること（IT-23）。
- **P-14：** トークンの失効（IT-08・IT-24）。
- **そのほか：** Linux CI（IT-17）、本物の HTTPS でのインストール（IT-18）。

## 7. セキュリティ上の懸念

| # | 懸念 | 扱い |
|---|---|---|
| S-1 | GitHub の前提（P-1〜P-17）が誤っている。特に、回避者がタグの作成に効かない、または効きすぎる | 統合テストの停止条件。architecture の 3 章の代替案 |
| S-2 | Publisher App の Contents: write は、ブランチへの push も含む | `main` はブランチの ruleset（回避者なし）で守る。ほかのブランチへの push は、PR を経なければ `main` に入らない。鍵は `publish` environment だけ |

| S-4 | テストの設定・鍵が本番に混ざる | 別のリポジトリ・App・鍵。本番のコードに切り替えの経路を作らない（W7）。IT-28 |
| S-5 | 2 つの App の鍵の管理の負担 | ローテーションの手順（手順書 C-6）。漏えいのときの停止（architecture の 8 章） |
| S-6 | **L-5（未解決）**：同じユーザーの権限による symlink の差し替えの競合。Java 21・macOS の制約。プロジェクトの外への新しいファイルの作成（0.2〜0.7%）。理論上の既存のファイルの置き換え。`L5RaceTest` で再現する | 統合テストのリスクの登録簿（RR-1）に記載した。**GitHub の統合テストが成功しても、L-5 は解決しない** |
