## 2. 指摘事項ごとの修正

### P4-H1 — 必須チェックの偽装（High）

**修正前の問題**
- ruleset の必須チェック（`validate`・`approvals`）は、名前だけで指定されていた。
- PR に含めたワークフローの同じ名前のジョブで、満たされる可能性があった。
- GitHub Actions のジョブのチェックは、どのワークフローのものでも GitHub Actions の App として報告される。そのため、名前に App を加えても区別できない。

**変更内容**
- `registry-template/.github/workflows/validate.yml` を 3 つのジョブに分けた。
  - `validate`・`approvals`：PR をデータとして読む。秘密情報は無く、`contents: read`・`pull-requests: read` だけ。
  - `report`（新設）：
    - PR のチェックアウトも、ビルドも、ツールの実行もしない。前の 2 つのジョブの結果（`needs.*.result`）だけを使う。
    - 秘密情報を使うのはこのジョブだけ。App の秘密鍵は、environment `registry-checks` の秘密情報。
    - レジストリ専用の GitHub App のトークンを作り、`checks: write` に限定する。それを使って、チェック `registry/validate`・`registry/approvals` を PR の head SHA に付ける。
    - PR の現在の head が、この実行のコミットと違えば、何も報告しない。
- `github-settings/main-ruleset.json`：必須チェックを `registry/validate`・`registry/approvals` に変え、`integration_id`（App の ID）を指定した。
  - 雛形の値 `0` は仮の値で、GitHub と `check-settings` が拒否する。
- `createscript-registry-tool`：
  - `GitHubSettings.kt`（新規）と `check-settings --ruleset` を追加した。
    - 次のものを拒否する：`integration_id` が無い・0・GitHub Actions の App（15368）、`bypass_actors` がある、承認が 2 未満、`dismiss_stale_reviews_on_push`・`require_code_owner_review`・`require_last_push_approval`・`strict` のどれかが無い。
  - `GitHubSettings.satisfied` は、GitHub の文書にある必須チェックの判定のモデル（同じ名前・同じ App・head のコミット・最後のものが成功）。
- 多層の対策：
  - `validate-pr --from-fork true` のとき、`.github/` を変える PR を拒否する。ワークフローは、head のリポジトリと base のリポジトリが違えば `true` を渡す。
  - GOVERNANCE.md は、fork のワークフローの実行に「すべての外部の協力者」の承認を求めるように改めた（以前は初めての貢献者だけ）。
- 守ったこと：
  - `pull_request_target` の信頼の境界（main のワークフロー、PR はデータだけ）。
  - `run:` の中に `${{ }}` を書かない。
  - アクションは SHA で固定（新しい外部のアクションは加えていない。App のトークンは openssl と curl で作る）。

**テスト**
- `GitHubSettingsTest`（4 件）：
  - 名前だけの ruleset は、PR のワークフローの同じ名前のチェックで満たされる（修正前の再現のモデル）。
  - App を指定した ruleset は、それでは満たされない。
  - 古いコミットへの App のチェックは数えない。
  - 後から報告された失敗が優先される。
  - GitHub Actions の App の ID の指定を拒否する。
  - 雛形は「App の ID が未設定」だけが問題になる。
  - fork の PR による `.github/` の変更を拒否する。
- `TemplateTest`：
  - PR を読むジョブは、秘密情報・`vars`・書き込み・environment を持たない。
  - 秘密情報を使うジョブは、チェックアウト・ビルド・ツールを使わない。
  - `report` は必須チェックの名前で、head SHA に報告する。
  - 外部のアクションは SHA で固定。
  - `run:` の中に式が無い。
- `RegistryToolTest`：`check-settings` が雛形で失敗する（App の ID が未設定）。
- 結果：すべて成功。

**修正後の判定:** 修正済み・**実環境未検証**。

**未検証の事項**
- `integration_id` を指定した必須チェックで、GitHub が実際に別の App のチェックを数えないか。
- `pull_request_target` のジョブから environment の秘密情報を使えるか（デプロイの参照が main になるか）。
- App のトークンで、fork の PR の head SHA にチェックを作れるか。
- `gh api --paginate --slurp` が、ランナーの gh で動くか。
- App の作成と、そのインストール。

**残存リスク**
- App の秘密鍵を持つ人は、チェックを作れる（environment に限定）。
- 管理者は、ruleset と App を変えられる。
- `report` は `needs.*.result` を信じる。前の 2 つのジョブの中のツール・依存が乗っ取られれば、偽の結果になる（P4-M3 の対策で低減）。

### P4-M1 — CODEOWNERS による自己 PR のデッドロック（Medium）

**修正前の問題**
- CODEOWNERS は `*` と `/packages/` が `@dog7dog` だけで、`require_code_owner_review` があった。
- そのため、運営責任者が作成した PR は、コードオーナーの承認を満たせなかった。

**変更内容**
- `CodeOwners.kt`（新規）：CODEOWNERS は `* @…` の 1 行だけで、所有者の集合が `maintainers.json` のメンテナーと一致しなければならない。
  - メンテナーが 0 人の間は、運営責任者だけ。
  - チーム・重複・ほかの行を拒否する。
- `LoadedRegistry.load` がこれを検査する。そのため、`check-repo`・`validate-pr` で、maintainers.json だけを変えた PR は止まる。
- 雛形の CODEOWNERS を、立ち上げの前の形（`* @dog7dog`）に変えた。
- ruleset の `require_code_owner_review: true` はそのまま。メンテナー全員がコードオーナーなので、作成者以外のメンテナーが承認できる。
- 規則の整合：
  - 作成者本人の承認は数えない（GitHub と `check-approvals`）。
  - パッケージの持ち主の承認は数えない（`check-approvals`）。
  - 運営の変更には、運営責任者が作成者か承認者であることが必要（`check-approvals`）。
  - メンテナーが 3 人未満なら、登録・更新・公開を拒否する（従来どおり）。
  - 管理者による回避を前提にしない（`bypass_actors: []`、立ち上げの後は回避が不要）。
- GOVERNANCE.md・SIGNING.md を改めた（運営責任者も署名できる。公開の PR はほかの 2 人が承認する）。

**テスト**
- `CodeOwnersTest`（4 件）：
  - 整合の検査（足りない・余分・2 行・チーム・重複・ファイルが無い・立ち上げの前）。
  - どの作成者にも、作成者以外のコードオーナーが必要な数以上いる。
  - 運営責任者の運営の PR は、bea・chen の承認で通る。運営責任者の自己承認は拒否する。
  - 持ち主のメンテナーの承認は数えない。
- テストの雛形（`ToolFixtures`）も、メンテナー全員の CODEOWNERS を書くようにした。
- 結果：すべて成功。

**修正後の判定:** 修正済み・**実環境未検証**（GitHub の CODEOWNERS の判定は確かめていない）。

**残存リスク**
- GitHub の設定だけでは、運営責任者の関与を強制できない（`check-approvals` に依存する）。
- 個人のリポジトリでは、持ち主が設定を変えられる。

### P4-M2 — 古い index への戻りと、緊急の失効（Medium）

**修正前の問題:** オンラインで取得に失敗すると、保存してある期限内の index を `note:` を付けて使った。

**変更内容**
- `RegistryClient.lookup`：オンラインで取得に失敗したら、`Unavailable(NETWORK)` を返す。
  - 保存した index があれば「使わなかった。使うなら `--offline`」と知らせる。
- `--offline` のときだけ、保存した期限内の index を使う。`note: offline: using the registry index saved before (…); packages removed and versions yanked after <generated> are not known` と、限界を示す。
- 変わらないもの：署名・serial・期限・履歴の検証。保存した index のほうが新しい場合の扱い（受け取った古い index は使わず、保存したものを使う）。
- 動作:

| 場面 | 動作 |
|---|---|
| オンラインの `install <名前>@<版>` | 69 で失敗する |
| 直接の指定・ロックファイルからの復元 | 「審査の状態を確かめられない」と警告する（古い index で「審査済み」とは言わない） |
| ロックファイルからの復元そのもの | S8.2 と同じ（index に依存しない） |

**テスト**
- `RegistryInstallTest.aNetworkFailureDoesNotRevivePackagesRemovedLater`（新規）：
  - 削除を含む新しい index を取得できないとき、名前でのインストールは 69 で失敗し、何も変えない。
  - 直接の指定は「確かめられない」になる。
  - `--offline` は保存した index を使い、限界を示す。
  - 通信が戻れば、新しいインストールも復元も、削除として拒否する。
- `RegistryClientTest`・`RegistryCliTest`：通信の失敗の期待値を新しい動作に改め、CLI で 69 と `--offline` の案内を確かめた。
- 引き続き成功しているもの：yanked・removed、ロックファイルの復元、明示的なオフライン、キャッシュの更新中の強制終了（段階ごとの停止と、SIGKILL）、GitHub の直接指定の互換。
- 結果：すべて成功。

**修正後の判定:** 修正済み。

**残存リスク（限界）**
- `--offline` では、保存した後の削除・取り下げを知り得ない。
- 初めて使うとき、またはキャッシュを消した後は、古いけれど期限内の署名済み index を受け入れうる（P4-I2）。攻撃者は通信の経路か GitHub の Release を握っている必要があり、期間は最長で `indexValidityDays`（雛形は 30 日）。
- 期限内の index を利用者に届かせない妨害は防げない（利用者は失敗に気づく）。
- `indexValidityDays` は短くしていない（署名する人の負担との兼ね合い。運営で決める）。

### P4-M3 — Gradle の依存の検証（Medium）

**修正前の問題**
- Maven の依存を検証せずに取得していた。
- 書き込みのトークンを持つジョブの中で、Gradle を動かしていた。

**変更内容**
- `gradle/verification-metadata.xml`（新規）：
  - 53 のコンポーネント・すべての成果物に SHA-256。`verify-metadata` は true。
  - 内容：Kotlin のプラグイン・コンパイラー、foojay、JLine、JUnit など。
  - ローカルの Gradle のキャッシュから `--offline --write-verification-metadata sha256` で作った。
  - 署名の検証（`verify-signatures`）は、鍵の取得に通信が必要なので入れていない。
- 雛形のワークフロー：Gradle を動かすすべてのステップで、次のことをする。
  - `WRAPPER_JAR_SHA256` で `gradle-wrapper.jar` を照合する。
  - `distributionSha256Sum` があることを確かめる。
  - `verification-metadata.xml` があることを確かめる（消されると、検証が無効になるため）。
  - `--dependency-verification strict --no-build-cache` で実行する。
  - `actions/cache` と `setup-java` の `cache:` を使わない。
- `publish.yml` を 3 つのジョブに分けた。
  - `check`：読み取りだけ。ツールを作る。
  - `release`：書き込みのトークンを持つ唯一のジョブ。Gradle もツールも動かさない。`sha256sum -c` と `gh release create` だけ。
  - `verify`：読み取りだけ。
  - ファイルは、`check` が出力した SHA-256 で照合してから公開する。

**テスト**
- `TemplateTest.dependencyVerificationIsComplete`：メタデータがあり、すべての成果物に SHA-256 があり、`distributionSha256Sum` がある。
- `TemplateTest.workflowsFollowTheSafetyRules`：wrapper の値が、このリポジトリの jar の SHA-256 と同じ。すべての `./gradlew` が strict でキャッシュなし。キャッシュを使わない。書き込みのジョブはビルドしない。
- 依存の検証が失敗する試験（手動、リポジトリの一時的な写しで実施）：

| 試したこと | 結果 |
|---|---|
| `kotlin-stdlib-2.0.0.jar` の SHA-256 を書き換えた | 終了コード 1、`Dependency verification failed for configuration ':createscript-core:compileClasspath'` |
| 元に戻した | 0 |
| メタデータを削除した | 0（検証されないので、ワークフローは削除を拒否する） |

- 全体のビルドを `--dependency-verification strict` で実行し、成功した。

**修正後の判定:** 修正済み（ワークフローの部分は実環境未検証）。

**未検証の事項**
- Linux の CI（`ci.yml`）で、同じメタデータで検証が通るか。プラットフォームに依存する成果物は見当たらない（`kotlin-native-prebuilt` は POM だけ）が、確かめていない。
- `WRAPPER_JAR_SHA256`（`cb0da675…56b8`）が、Gradle 8.8 の公式の wrapper の checksum と一致するか。通信しないので、照合していない。立ち上げのときに照合する手順を GOVERNANCE.md に書いた。

**残存リスク**
- メタデータを作った時点の依存がすでに改ざんされていれば、それを固定してしまう（初回の信頼）。
- 署名の検証は無い。
- `setup-java` が配布する JDK と、ランナーの環境は信頼の前提。

### P4-M4 — 承認の再検査（Medium）

**修正前の問題**
- 承認の再検査は手動の再実行で、認証なしの API を使っていた。
- 古い実行を再実行すると、古い head SHA を対象にした。

**変更内容**
- `validate`・`approvals`・`report` の各ジョブが、最初に `gh api repos/…/pulls/N` で PR の現在の head SHA を読み、イベントの SHA と違えば止まる。`report` は何も報告しない。
- レビューは、ジョブのトークン（`pull-requests: read`）で `gh api --paginate --slurp` で読む。認証なしの API の呼び出しは無い（テストで確認）。
- API の失敗は、ステップの失敗になる（`gh` の非 0 の終了、`set -euo pipefail`）。エラーの応答・空・壊れた JSON は、ツールが拒否する。
- `publish.yml` の `check` ジョブで、公開の前に次のことを確かめる。
  - push されたコミットが、ちょうど 1 つのマージ済みの PR から来ている。
  - その PR の head のツリーと、公開するコミットのツリーが同じ。
  - PR のレビューで、`check-approvals` が通る（base は push の前のコミット、head SHA は PR の head）。
- 作成者の除外・利益相反の除外・古いコミットへの承認の除外は、`check-approvals` の従来の規則。

**テスト**
- `RegistryToolTest.apiErrorsFailTheApprovalCheck`：レート制限のエラーの応答・空・壊れた JSON・user の無いレビューで、どれも成功にならない。`--from-fork` の不正な値。
- `TemplateTest`：PR を読むジョブに現在の head の照合がある。api.github.com を呼ぶ行には Authorization がある。publish の `check` に、承認の再検査とツリーの照合がある。
- 既存の `ApprovalsTest`：古いコミットへの承認・作成者・持ち主・変更の要求。
- 結果：すべて成功。

**修正後の判定:** 修正済み・**実環境未検証**。

**未検証の事項**
- `commits/{sha}/pulls` が、squash・rebase のマージ後のコミットから PR を返すか。
- `git fetch origin <PR の head SHA>` が、マージ後に取得できるか。
- `--slurp` の形。
- `labeled` で始まる実行の内容。
- GITHUB_TOKEN のレート制限の実際。

**残存リスク**
- レビューは依然として `pull_request_target` を起動しないので、承認の後にラベル `recheck` が必要（運用）。
- ラベルを付けられるのは triage 以上の権限を持つ人。

### P4-L5 — 立ち上げの前の承認（Low、追加で対処）

**修正前の問題:** メンテナーが 0 人のとき、`check-approvals` は何も求めなかった。

**変更内容:** 運営責任者が `maintainers.json` にいなければ、`check-approvals` は必ず失敗する。GOVERNANCE.md の立ち上げの手順に明記した。

**テスト:** `CodeOwnersTest.nothingIsApprovedBeforeTheBootstrap`（成功）。

**判定:** 修正済み。

## 3. L-5（P4-L1）の調査

### JDK 21 の標準 API

- `SecureDirectoryStream` は、ディレクトリの記述子を基準にした操作（`newDirectoryStream(相対, NOFOLLOW_LINKS)`・`newByteChannel`・`move`（renameat）・`deleteFile`）を提供する。使えれば、開いた後のパスの差し替えの影響を受けない。
- ただし、**ディレクトリを作る操作は無い**。作業用のディレクトリの作成は、名前による操作のまま残る。

### OS ごとの利用の可否

| OS | 状況 |
|---|---|
| macOS（Darwin 25.3.0、aarch64、Temurin 21.0.12.1） | **使えない（実測）**。`Files.newDirectoryStream` が返すのは `sun.nio.fs.UnixDirectoryStream` で、`SecureDirectoryStream` ではなかった（一時ディレクトリでの試験プログラム）。この JDK は macOS で、記述子を基準にした安全なディレクトリの操作を、標準 API として提供していない。理由は JDK の実装の内部（openat 系の対応の判定）によるもので、ここではそれ以上は確かめていない |
| Linux | JDK の実装は `SecureDirectoryStream` を提供するとされるが、**未検証** |
| Windows | `SecureDirectoryStream` は提供されない見込み。**未検証** |

### 判断

- 主な対象の macOS で使えない。Linux だけの別の経路を加えると、既存の安全策（fileKey の照合・案 C）との組み合わせを検証し直す必要がある。どちらも低リスクとは言えないので、**今回はコードを変えていない**。
- native API・FFM・JNI は使っていない。
- 既存の安全策はそのまま（弱めていない）。
